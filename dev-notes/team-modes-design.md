# Agent Team 三种协作模式设计

2026-11-04。本文细化 [二开需求方案](requirements-v1.md)中的 Agent Team 高优先级范围，结合 cuican-aide、NanmiCoder/dsh-agent-teams 和 Contexera/dsh-agent-team 的源码确定产品语义与首批实现。

## 1. 三种模式的使用场景

| 维度 | 工作流 | 专家团 | 办公室 |
|---|---|---|---|
| 用户目标 | 稳定重复地完成一类工作 | 为一个复杂问题得到可信结论或成果 | 让固定成员长期协作推进一个项目 |
| 典型场景 | 周报、发布检查、素材生产、审批流程 | 技术选型、故障诊断、方案评审、多角度研究 | 产品研发小组、运营团队、持续创作团队 |
| 编排方式 | 保存的节点、输入输出、依赖和人工关卡 | 团长围绕本次目标动态分工和汇总 | 成员持续存在，按话题讨论、点名和交接 |
| 谁决定下一步 | 流程定义与节点结果 | 团长依据目标、结果与剩余问题 | 项目负责人、成员职责及用户指令 |
| 用户主要界面 | 流程图、当前节点、待确认内容、运行历史 | 团长主会话、专家贡献、证据和最终结论 | 讨论区、成员列表、话题、待处理事项与成果 |
| 成员生命周期 | 服务于一次流程执行，可复用角色定义 | 服务于本次目标，完成后归档本次协作 | 独立于一次目标，持续保留身份与职责 |
| 完成标准 | 终点节点成功，交付物通过校验 | 团长交付，必需专家结果与验证齐全 | 每项工作单独完成，办公室继续存在 |
| 恢复重点 | 从最后已提交节点继续，保留人工决策 | 恢复本次分工、成员结果与汇总结论 | 恢复长期成员、话题、注意事项和所属项目 |

### 工作流

适用于步骤和输入输出已经清楚的重复工作。例如“收集本周材料 → 各负责人补充 → 生成周报 → 人工确认 → 输出文档”。用户编辑流程模板，再以具体输入启动一次执行。节点采用不同 Agent 执行，节点之间传递明确成果，验证失败回到明确修订步骤。

人工关卡绑定审阅过的输入版本。用户批准后修改了上游成果，原批准需要重新核对。重复运行产生新的执行记录，历史运行保留自己的配置、输入、输出和决策。已有外部操作通过回执恢复，避免断线后重复提交。

### 专家团

适用于目标清楚但解法与分工需要分析的问题。例如“从成本、架构和安全三个角度选择数据库”。用户向团长描述问题，团长提出成员及任务计划，经确认后安排独立调查，检查矛盾与缺口，再给出综合结论。

默认主会话由团长回复，用户按需展开专家自己的观点、证据和执行过程。专家可以提出不同结论，团长说明取舍依据。专家发现信息不足时向团长报告，团长集中向用户澄清。必需成员失败会影响整体完成判断。

### 办公室

适用于持续推进的团队。例如长期合作的产品经理、设计师、工程师和审阅者。用户进入一个办公室，围绕多个话题讨论，点名成员处理事项，负责人协调交接。某项工作完成后，团队和其他话题继续存在。

成员身份、职责、项目参与关系和关注的话题分别持久化。公共讨论、明确点名、私有澄清具有不同的通知范围。成员共享已发布事实，各自的内部记忆通过受控摘要贡献给公共讨论。办公室需要把“收到消息”“正在处理”“已经交付”“已被验收”分别记录。

| 项目 | 已查到的实现重点 | 最适合吸收的部分 | 接入时的约束 |

## 3. 实现选择

首批内置插件使用固定版本的 NanmiCoder 实现，包装为仓库自己的可选 bundle，由应用分发和插件页管理。Host、工具及 Client 复用上游，当前 0.2.2-alpha.3 通过补丁和子代理公开接口适配。初次接入问题见第 7 节，当前交付状态见第 9 节。

首批产品验证对象是专家团。先打通创建计划、修改/批准、真实成员执行、依赖调度、贡献展示、停止与归档恢复。工作流模板随后复用已经验证的 DAG 能力；节点级人工关卡及可恢复执行按独立协议补齐。

办公室采用 Contexera 的长期领域设计作为需求依据，先明确成员与项目生命周期、消息通知、验收责任和权限，再接入。将其整体安装到当前 profile 前，需要验证 scoped preset、Remote、当前 DSH API 和 sandbox 策略。一个协作实例固定一个状态 owner 和执行实现，成员与工作项不能由两个插件同时调度。

界面统一使用“团队”入口，用户创建时选择模式。专家团提供目标与成员，工作流提供模板与运行输入，办公室提供团队职责与项目。运行中均能查看成员、工作项和成果，但各模式保留各自的完成与恢复标准。

## 4. 协作规则

1. 每个工作项有明确执行成员、输入、成果要求和状态。任务依赖由 Host 判定就绪，修改 owner 时终止旧尝试的继续写入资格。
2. 需要独立验收的工作由不同成员审阅。团长汇总保留各成员的来源，对缺失、失败与分歧给出明确说明。
3. 用户的批准绑定具体计划或成果版本。后续相关修改重新确认其适用性，原决策记录保留。
4. 发送消息、成员收到消息、模型消费消息和完成工作分别观察。普通状态刷新不会反复唤醒成员。
5. 停止团队阻止新分发，并跟踪在途成员的实际取消结果。归档保留历史、成员结果与文件引用。
6. 模型、权限和工作空间继承通过明确配置确定。团队模式本身不改变用户选择的执行权限。
7. 面板展示从状态 owner 读取的已提交事实，模型自然语言完成声明仍需与工作项和成果核对。

## 5. 各模式首个验收案例

| 模式 | 输入 | 必须验证的结果 |
|---|---|---|
| 专家团 | 三个角色评审一个真实仓库变更 | 真实成员分别产出证据，团长引用其结论，失败和重试可追溯，刷新后贡献仍存在 |
| 工作流 | 材料整理、成稿、独立审阅、人工批准、交付 | 顺序和依赖正确，批准前停止在关卡，重启后核对原输入继续，外部提交去重 |
| 办公室 | 同一小组连续处理两个相关话题 | 成员身份保持稳定，@对象准确收到消息，公共与私有消息范围正确，单项完成后仍能继续合作 |

## 6. 分批落地

| 批次 | 范围 | 放行条件 |
|---|---|---|
| I1 内置包装与兼容 | 固定上游版本，接入分发/插件页，隔离 profile 中启用 | 当前 Host 兼容检查、实际 Loader、工具与 Client 加载通过 |

## 7. 初次接入验证与适配依据

2026-11-04 对 NanmiCoder 0.1.28 完成了临时 bundle 包装、依赖解析、构建和隔离 headless 运行。包装状态下 `pnpm run build` 的 10 项构建任务通过，但真实 Loader 在安装成员保护逻辑时抛出 `unsupported Harness subagent contract (cannot install complete retired-member guard)`。当前 Host 版本为 0.2.2-alpha.3。错误发生在团队工具注册之前，成员模型请求数为零，构建结果不能作为运行验收。

初次失败后曾撤回临时产品注册及依赖，完成适配后重新接入。需求、源码对照和失败证据保留在本设计中。初次实验确认插件化架构可承载三种模式，同时原版上游需要兼容改造。第 9 节记录已完成的适配。

| 接入点 | 上游依赖 | 当前 Host | 必须保持的行为 |
|---|---|---|---|
| 成员再次接收任务 | `followup` 或 `dsh.subagent.queuePrompt` / `dsh.subagent.deliverPrompt` 符号方法 | `sendMessage` 支持 steer；没有同等公开的 Host 排队接口 | 忙碌时排队与当前回合引导分开，保留来源、顺序和接受回执 |
| 退役成员保护 | 上游包装全部消息投递方法，缺少必要方法即拒绝启动 | 投递入口已经调整 | 退役后所有投递路径拒绝，卸载恢复注册，旧尝试不能继续修改团队 |
| 指定成员回收 | `drainChildren` 或 `drainContinuableChildren` | `interrupt` 发出取消请求；`drainDescendants` 面向整个树 | 只回收所属成员，等待实际退出，保留其他子任务 |
| 上游 Web 验证夹具 | 关闭 `headless-startup` | 当前 `sandbox-policy` 依赖 `headlessStartup` | 先更新夹具的 profile 组合，再判断 Web 产品行为 |

上游 `src/harness-compat.ts` 是适配入口。当前 Host 的公开行为以 [SubagentRuntime](../packages/subagent/subagent/src/index.ts)、[manager](../packages/subagent/subagent/src/manager.ts)和 [子代理文档](../packages/subagent/subagent/README.md)为准。不得通过访问私有 manager、冒用浏览器用户来源、取消保护检查或扩大取消范围来绕过错误。

### 下一批代码变更

1. 在子代理服务中确认并提供有类型的 Host 消息排队、指定 activation 回收和成员准入扩展点，完整定义来源、取消、接受与关闭的时序。复用现有 manager 的投递和释放实现，补充关闭期间投递、冷恢复、重复取消及跨树拒绝测试。
2. 在固定版本上游的适配层接入这些公开接口，保留可审计补丁和 MIT 署名。先通过无 API key 的确定性成员执行用例，覆盖两次唤醒、忙碌排队、退役拒绝和实例卸载。
3. 恢复可选内置 bundle 与应用依赖，限定首版为专家团；验证插件开关、审批、成员贡献展示和刷新恢复。用户未选择时保持当前 profile 的模型输入。
4. 增加 Session 驱动的 keyless 快照和实际浏览器验收，再扩展工作流和办公室。若需要新增持久事件，同批评估格式兼容、读者行为及两套 SDK。

### 首版界面与交互约束

创建入口选择“专家团”，填写目标、交付物要求和可选角色。提交后显示可编辑计划，明确成员、任务依赖、模型和权限。批准前不派发执行工作。团长消息进入主会话，侧栏依次呈现成员状态、待审阅事项、工作项和成果。展开成员查看独立贡献和证据，返回时保留主会话位置。

待审阅、执行中、需要用户补充、部分失败、已交付、已停止和已归档分别展示。部分成员失败时允许重试对应工作项或调整计划；重新指派必须创建新尝试。停止操作立即显示停止中，成员退出确认后显示已停止。刷新恢复以持久事实为准。错误提示携带具体成员、工作项和可执行的处理方式。

工作流第二阶段采用模板编辑与单次运行两个视图，明确节点输入、产物和批准版本。办公室第三阶段采用项目讨论与话题视图，突出稳定成员、定向通知、待验收项和交接记录。三种模式共享已有布局、国际化和基础组件，各自保留独立的运行状态与完成规则。


## 8. 最新版本复核

2026-11-04 重新查询 npm dist-tags，并 fetch 两个插件及 DSH 官方分支。NanmiCoder 默认分支与 npm latest 均为 0.1.28；Contexera 默认分支与 npm latest 均为 0.2.6；DSH 官方 master 与本地基线均为 0.2.2-alpha.3。三个仓库相对本轮首次检查均无更新。DSH 的 npm latest / next 为 0.2.1-rc.5，alpha 为 0.2.2-alpha.3，渠道名称必须与实际版本一起判断。

当前 Host 上的 NanmiCoder 结论沿用第 7 节。Contexera 0.2.6 使用 npm 发行包，在独立 DSH_HOME 下经过当前构建的 `dsh --profile headless` 加载，补入工作空间服务后能够创建、暂停和恢复成员。但成员首轮执行在 `member-runtime.js` 的 `assembly.tools.filter(...)` 处失败，产生 `Cannot read properties of undefined (reading 'filter')`，该成员没有到达模型调用。普通主会话的成功输出不能作为成员执行证据。

该异常来源已通过 `agent/error` 堆栈定位。当前 [system-prompt](../packages/core/system-prompt/src/index.ts) 的 `system-prompt/assemble` waterfall 传递 `PromptPresentation`，在该阶段结束后附加已经收集的工具并返回完整 `PromptAssembly`。Contexera 的成员工具策略仍把 waterfall 结果当作含 `tools` 的完整对象处理，需要适配当前工具 schema 提供机制，同时保留其成员执行授权检查。

NanmiCoder 的 [兼容清单](https://github.com/NanmiCoder/dsh-agent-teams/blob/main/compatibility.json)推荐 DSH 0.2.1-rc.2，并列出 0.2.1-rc.3；0.2.1-rc.5 发行物仍带 `dsh.subagent.deliverPrompt` 和 `drainChildren`。该渠道属于较早的 0.2.1 系列，切换到它会改变当前 0.2.2 基线，不能按普通向前升级处理。Contexera 的声明范围为 `>=0.2.1-rc.2 <0.2.2`，实际行为需要独立运行验证。


### 发布渠道组合实测

在独立临时目录安装固定的 DSH 0.2.1-rc.5 及两套插件，补齐匹配版本的 peer dependencies，所有测试均使用确定性适配器，不调用外部模型 API。本次未调整项目的依赖、Host 版本或用户 profile。

| 插件 | 当前 DSH 0.2.2-alpha.3 | npm 默认 DSH 0.2.1-rc.5 |
|---|---|---|
| NanmiCoder 0.1.28 | 加载时缺少完整退役成员保护所需的投递接口 | 上游 lifecycle 与 lifecycle-cold-restore 用例通过，共 15 次请求，其中成员请求 6 次；覆盖工作项完成、忙碌时消息排队、再次唤醒、成员权限及冷恢复 |
| Contexera 0.2.6 | Host 加载与成员创建、暂停、恢复成功；成员执行在工具 schema 过滤阶段失败 | 创建成员后实际收到成员模型请求，包含 7 个 team 工具，记录 assistant/message 与完成的 turn/end；成员暂停和恢复成功 |

Contexera 的测试同时检查了成员 Session 的事件和模型请求，避免把主会话的成功回复当作成员执行成功。NanmiCoder 使用上游原始运行夹具。上述结果验证本次具体兼容缺口与基础生命周期，尚未覆盖真实模型质量、Web 交互、长期运行及全部产品验收项。

版本升级本身无法修复当前 0.2.2 接入，因为已经使用两个插件的最新版本。采用 0.2.1-rc.5 可以运行上述组合，但属于切换回较早内核；若维持当前项目基线，仍需分别适配 NanmiCoder 的子代理接口和 Contexera 的工具 schema 提供方式。三种产品模式的划分继续有效，执行内核选择需按这一验证结果确定。


## 9. 当前专家团实现

内核保持 0.2.2-alpha.3。可选内置包 `@deepseek-ai/dsh-agent-teams-bundle` 随 CLI 分发，插件页显示“专家团”。它固定依赖 NanmiCoder 0.1.28，仓库 pnpm 补丁适配成员创建参数与初始化检测，并修正提示词段落分隔。子代理服务增加带持久来源的 `followup` 和指定分支 `drainChildren`，沿用现有投递、冷恢复与释放实现。停止指定成员时拦截该分支的后续准入，并等待已经受理的启动及资源清理。

默认工作空间状态目录为 `.agent-teams`，成员 provider 为 `spawn`，最多八名成员，成员嵌套委派深度为零。配置可通过 profile patch 调整。计划批准、成员工作项、独立贡献和团队面板使用上游现有交互。插件目录、许可及其他配置说明见 [包文档](../packages/bundle/agent-teams/README.zh.md)。

## 10. 用户定义的专家团

专家团先保存团队定义，再针对具体问题创建独立运行。定义包含团队名称、专业方向、协作要求、成员名称、专业角色和执行职责；同一团队可复用处理多个问题。固定的是专业分工，本次任务由团长根据问题拆解，批准后分派给相应专家。模板更新影响后续运行，已有运行保留自己的成员与任务记录。

插件详情页提供创建、编辑、删除和使用入口。使用入口在选定工作区创建独立会话，内部通过 `/agent-teams --profile` 提交模板与问题，受理后直接打开会话。模板复用上游 `profiles` 配置，通过 DSH 设置服务保存并校验版本，避免并发编辑静默覆盖。带空格的模板名在命令中引用并完整解析。

本地验收创建了“CrewON 产品专家团”，固定产品负责人、交互设计师、前端架构师三位成员。保存配置、重启读取、带空格名称调用、计划确认、三位真实模型成员执行与汇总均已验证；同时保留无密钥的模板保存、冲突、删除和运行恢复测试。使用入口直接创建并提交任务；创建或提交失败保留问题，已创建的会话可打开检查，避免不确定结果下重复提交。

直接发起入口已完成本地 Web 实测：从已保存团队填写问题后发起，自动创建新会话并进入计划，批准后 4/4 工作项完成。一次测试中的汇总工作项被共享任务池中的前端专家领取，队长在全部交付后完成最终复核。Web 与桌面 App 当前仍使用各自 profile 的团队配置，跨 profile 模板同步尚未实现。

## 11. 集成决策与首批验收

产品上交付一个「团队」内置插件。保留现有 bundle ID、专家团配置键和会话入口，在已有 `teams.mode` 下接入办公室和工作流。Host 按模式注册各自的运行适配器，分别持有状态与停用逻辑。共享工作区选择、模型和权限选择、状态组件及成果链接。团队页负责配置和历史，对话负责发起或继续交流，右侧呈现执行过程。

| 模式 | 运行实现 | 首版入口与范围 |
|---|---|---|
| 专家团 | 已适配的 NanmiCoder bundle | 继续使用现有创建卡片、复用模板与对话入口 |
| 工作流 | 优先验证 GM-HZ 的持久 DAG SDK，通过 CrewON Host 接入 Agent、审批和存储 | 团队页发布模板、填写输入、运行和查看历史。首版提供顺序与并行节点、人工确认和独立验证 |
| 办公室 | 隔离适配 Contexera 0.2.6 的长期成员、话题与验收机制 | 团队页创建办公室及成员，进入讨论后可定向 @，查看成员回应和交接。首版限定同一 Host 与工作区 |

工作流先行。当前 DSH 的 `workflowEngine` 负责一次调用内的脚本编排，工作流产品还需要不可变模板版本、运行历史、可恢复关卡和运行级权限。GM-HZ SDK 提供独立执行与存储接口，先验证最小发布运行、重启恢复和 Agent 网关，再接入团队页。首个模板采用“整理材料 → 起草 → 独立审阅 → 人工确认 → 交付”，审批绑定运行、关卡和被审阅的产物版本。浏览器验收覆盖批准前暂停、刷新与重启后恢复、拒绝路径、重复点击及一次交付。画布、定时和 Webhook 延后。

办公室随后单独验证 Host。先把 Contexera 的成员工具过滤迁移到当前工具 schema 扩展点，并让成员运行继承工作区权限。用同一办公室处理两个话题，核对重启后的成员身份、定向投递、跨话题隔离和独立验收。权限或成员首次模型请求验证失败时，办公室保持未启用。现有专家团可以继续使用，模式启用与失败状态分别呈现。

三者的衔接从显式引用成果开始。工作流产物可以附到办公室话题或专家团对话，专家团的结论可以作为一次工作流的输入。每次发起仍经过对应模式的入口及权限检查，记录来源及版本。自动跨模式调度、共享成员记忆和独立任务中心均留到后续评估。

工作流预检使用 npm 发行版 `@gm-hz/agent-dag-workflow@1.0.1`、Node 24.18.1 和独立临时目录。上游 README 示例缺少 `workflow.script.execute` 能力声明，编译器正确拒绝；补上声明后，三个节点全部成功，运行进入 `completed` 并返回预期结果。此验证使用内存存储，CrewON Host、持久审批和浏览器仍待验收。

工作流 SDK 的 SQLite 预检已覆盖固定发布版本、审批暂停、进程退出后继续和再次恢复同一运行。第一次恢复走批准分支，拒绝分支跳过；第二次返回既有完成结果，日志只有一次完成事件。该用例使用模拟审批网关，产品审批按钮及并发确认仍需在 CrewON Host 验证。

「团队」下可以提供独立的 Agent 定义设置。定义保存名称、职责、指令、技能引用和默认模型；使用时由当前工作区确定有效权限。办公室从定义创建长期成员，持有身份、会话和记忆。专家团从同一份定义创建本次运行的专家，工作流节点也可引用该定义。模板绑定稳定 ID，执行时固定定义版本和权限。既有内联角色仍可运行，只有用户选择复用时才关联定义。办公室成员的历史和记忆仍归所属办公室成员实例。

### 当前接入状态

「团队 → 工作流」保存起草、审阅和交付要求，并将每次输入和状态保存为独立运行。实现采用当前预设的原生 workflow 工具。起草后可并行审阅，批准后的交付另开一次原生执行。两段之间的审批和产物保存到当前 profile 的 SQLite，等待审批期间重启可以恢复，执行中的中断保留在历史。可复用定义和独立运行历史借鉴 [dsh_workflow](https://github.com/omdsh-dev/dsh_workflow)。

办公室仍须完成当前内核适配。Contexera 成员启动同时包含工具 schema 白名单和执行期 guard。当前 DSH 在组装 prompt 之前通过工具注册表解析可见工具，迁移时需要在解析阶段限制成员工具并保留原有执行期身份检查。成员启动中的强制全权限需要替换为明确的工作区权限，两个改动应在隔离 profile 验证后再启用办公室入口。
