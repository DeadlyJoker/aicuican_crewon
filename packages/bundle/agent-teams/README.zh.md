## 使用本包

“团队”默认显示在 Web 和 Desktop 插件管理中，未启用时也可见。启用后按提示重启配置。打开“团队 → 专家团”，预先定义专业方向、协作要求与成员职责。使用 `/create-expert-panel`（中文显示为“创建专家团”）提出待审查的可复用团队配置。运行已选团队时另行生成执行计划，其审查卡也能在启动前保存成员分工供复用。内部 `/agent-teams` 写法继续用于调用已有团队。在对话中输入 `@`，选择专家团，再输入问题并发送，所选团队显示为草稿内可删除的标签。发送后显示团队提及与原始问题，日志中的内部命令调用该已有团队，生成待审批的执行计划。沿用当前对话与附件。待确认计划显示在最新完成的回复下方，随后续回复移动，重新打开会话后恢复。成员与任务区域支持就地新增和折叠编辑。执行计划的审查卡片在新增和编辑成员时使用统一专家选择器，保存不可变预设版本及明确配置的模型路由，并保留当前任务职责。专家准备期间及成员编辑未保存时暂停审批。前置任务直接从实际任务列表勾选，排除自身和循环依赖，确认后创建成员并开始执行。右侧只用于查看详细进度，不再自动弹出。发送前删除标签即可按普通消息提交，已有团队继续由团长管理。

可以让助手设计可复用专家团，或选择“新建专家团”。内置 `create-expert-team` skill 和 `expert_team_save` 会在最新完成回复下方生成持久化审查卡片。卡片与团队页编辑器共用成员、目标、约束和交付要求字段。确认只保存一次所审查的配置，不会启动成员；修改、重新打开会话及 Host 重启都会保留草稿。编辑器提供五套可修改的场景模板。`expert_team_list` 可检索真实专家目录，方案会将选中的专家绑定到不可变的预设版本，原有内联角色继续兼容。

启用工具箱后，专家编辑器在基础预设之外提供技能、MCP 连接器和本地工具选择，已有权限选择会带入下一次保存的专家版本。能力发现失败时阻止保存；若专家保存成功但策略写入失败，表单保留草稿并明确提示版本已保存，可再次保存重试。未启用工具箱时，编辑器明确提示沿用基础能力。

自定义 profile 可在基础和应用 bundle 后加入 `@deepseek-ai/dsh-agent-teams-bundle`。通过 profile patch 覆盖 `agent-teams`，配置状态目录、成员 provider、成员上限或嵌套委派深度。默认值为 `.agent-teams`、`spawn`、八名成员和零层嵌套委派。

打开 **团队 → 专家**，按专业和分类搜索 331 位内置专家，查看职责、复制修改，或基于原生 Agent 预设保存自己的专家。完整职责只在查看或使用时加载。点击使用、示例问题或在输入框中通过 `@` 选择专家，会准备使用该专家预设的新普通对话，不会自动发送。原会话和草稿保持不变，从输入框带入的附件会在新会话中使用独立草稿身份。

专家团成员、工作流步骤和办公室成员共用同一个搜索选择器，直接列出内置专家与已保存专家。选择内置专家时按需注册不可变预设，无须先访问专家页。选择失败或取消会保留原绑定，准备期间暂停保存和其他草稿编辑，避免迟到结果覆盖别的成员或步骤。原生继承选项和早期预设继续可用。团队的目标、约束、交付和协作说明均可留空，保存时省略空值，已有包含空值的配置也可运行。

专家团、工作流步骤和办公室成员均可选择已保存的专家。修改会生成不可变预设版本，已有运行和历史保留原版本；办公室可为同一成员切换后续消息使用的专家。轨迹选择器读取实际子会话记录的预设，显示当时的专家名称和版本，选择旧版本会打开该子会话原有的原生轨迹。Web 与 Desktop 通过 `teamCatalogue.watch` 接收已提交的目录及历史变更，保留本地编辑草稿与导航位置。执行由原生 `agentPresets` 服务负责。内置素材的来源版本及 MIT 许可见 [assets/experts/UPSTREAM.md](assets/experts/UPSTREAM.md)。

本 bundle 的 `expertPromptMaxLength` 默认 32768 字符，`expertBuiltinBasePreset` 默认 `standard`。过长职责会明确拒绝，不会截断。创建指令与专家目录依赖原生 `agent-preset-registry`，Web 和 Desktop 配置已包含；自定义 headless 配置须显式添加。专家配置与不可变版本保存于 `team-experts.sqlite`，可复用团队审查草稿保存于 `team-authoring.sqlite`。确认操作校验版本，并能在保存成功但回执中断后核对已提交的配置。

## 理解实现

<details>
<summary>理解实现</summary>

bundle 挂载上游 Host entry 和 Client 编辑器。编辑器通过带版本校验的设置写入修改上游 `profiles` 字段，保存被拒绝时保留草稿，编辑角色时保留已有 profile 的其他字段。上游包拥有协调逻辑与工作空间状态。仓库补丁适配当前子代理 API 的 activation 创建及初始化。Host 负责带来源的队列投递和指定分支回收。模板修改用于后续团队创建和模型请求，已创建团队保留自己的成员状态。

</details>

## 保存工作流

在 **团队 → 工作流** 自由编排 Agent 任务和可选的人工审批节点。节点通过前置依赖组织串行与并行，名称和任务指令由用户定义。每次运行填写新的输入，并在所选工作区打开对话。对话中的审批卡片提供草稿和审阅意见，流程库列出近期运行并可打开对应对话。

Host 在人工决策前后分别调用所选预设的原生 `workflow` 工具。流程定义、输入、产物和决策保存在 profile 的 `team-workflows.sqlite` 中。Host 重启后仍能审批待确认的草稿。交付前，Host 只接受一次有效审批。Agent 工作期间重启会将该次运行标记为中断，需要重新发起。交付结果以 Markdown 显示在对话卡片中。

在对话的「轨迹」页展开「执行步骤」，可以查看实际执行依赖。选择 Agent 节点可查看任务输入、输出与状态，选择审批节点可查看送审材料和决定。

工作流的每一步都可以选择已有 Agent 预设。留空时沿用对话预设，已有工作流也是如此。如果所选预设已移除或不可用，执行会明确报错。

工作流步骤可增删、调整顺序、设置依赖和绑定已有 Agent 预设。满足前置依赖的 Agent 节点可并行运行。审批可以不设或设置多处，每次确认仅放行对应节点。旧版审批前后步骤继续按原定义运行。运行历史按工作流 ID 归档，执行和轨迹均读取该次运行保存的定义。点击执行步骤会在当前「轨迹」页切换到子 Agent 的原生时间线与事件列表，再点一次返回本次运行的轨迹。

工作流编辑器使用可拖拽节点画布。Agent 与审批节点通过端口连线定义执行依赖，属性面板编辑所选节点。节点位置独立于执行顺序保存，旧定义自动生成布局。画布及 Host 均拒绝循环依赖，运行历史和原生轨迹沿用原有归属。

团队页拥有独立纵向滚动区，内容宽度、页面标题、导航标签高度和新建按钮样式沿用自动化任务页。三种模式共用一个团队页标题，右侧按当前分类显示「新建专家团」「新建办公室」或「新建工作流」，下方切换分类，内容区省去重复的目录标题。办公室和工作流卡片使用与对话右侧栏一致的齿轮及设置提示。卡片操作图标在悬停或键盘聚焦时显示，触屏始终可见。专家职责保留在编辑器中，成员小头像提供姓名与角色提示。

在工作流首个步骤开始前，控制器读取保留的 Session 历史，避免重复注入已记录的上下文。历史读取失败时，停止该步骤，不添加上下文。

专家作为团队成员运行时，会自动获得认领任务、汇报结果、更新自身任务和读取团队状态所需的四项原生协作工具，即使其预设使用了工具箱白名单。运行时核对当前成员身份后才提供这些工具。其他能力仍受专家权限限制；普通专家对话和工作流步骤不会获得团队角色默认工具。

## 长期办公室

在团队 → 办公室配置固定角色和已有 Agent 预设，然后从所选工作区进入。办公室保留自己的对话与成员身份。输入框中从 @ 菜单选择成员后，通过命令通道直接投递，回复显示在对应消息下。首次点名创建成员的原生可续聊 Session，后续消息及 Host 重启后继续使用同一 Session。轨迹页可选择成员并查看原生执行记录。

办公室配置与消息结果存于 profile 下的 team-offices.sqlite，模型历史和工作区权限继承由原生 Session 管理。每个成员在同一对话范围内同时接受一条未完成请求，同一角色可在不同话题中并行工作，重启时中断的请求标记为已中断。投递会校验收件人属于当前办公室。本适配器使用 DSH 原生子 Agent，Contexera 的长期成员模型作为设计参考。

办公室成员表单按身份字段分组，职责支持多行编辑，弹窗操作区独立于滚动内容。对话回复使用主题适配的气泡，成员身份与执行状态显示在气泡上方。

办公室设置在当前对话中编辑名称、用途、成员名单、角色、职责和可选组长，团队页复用同一套可折叠成员表单。已有成员保留身份和名称。切换专家后，后续大厅与话题消息使用新的执行会话，历史消息和执行中的任务保留原会话与专家版本。职责调整对后续请求生效。新成员可选择预设，并使用稳定身份处理保存重试。移除成员保留历史消息和会话，仍有待处理任务时拒绝移除。项目和收件箱通过已有账本同步保存后的成员名单。

## 办公室项目与收件箱

项目适配器复用 Contexera `dsh-agent-team` 0.2.6、提交 `08c3e4b6ec41382941236e461cde4ffede234ffd` 的账本和操作校验。选取的源码及 MIT 许可位于 `src/contexera-domain`，该目录说明记录编译兼容调整。项目、讨论话题、消息点名、未读标记、重复提交与版本校验均由该账本处理。入口位于办公室卡片的“项目与收件箱”操作。

已有办公室首次访问项目时，幂等导入成员身份及大厅原生 Session ID。每个办公室在当前存储后端使用独立的 `crewon_office_<id>` 数据域。项目和 Inbox 话题行打开各自固定的主对话，每个话题拥有独立的成员 Session，重复打开及 Host 重启后继续恢复。发布时选择成员，会通过办公室命令投递，并将原生成员回复记入该话题。打开话题确认用户未读标记，查看成员收件箱保留该成员的未读状态。话题对话按时间显示完整账本消息，包括旧大厅客户端写入的回复。等待中的原生投递跟随其来源消息展示，结果回填后由账本消息接替。读取话题保持只读，可见对话单独按已显示水位确认未读，并逐批处理账本的读取上限。当前集成讨论话题，上游任务、Claim 与私信运行时另行接入。

## 对话范围与详情

候选会话已属于办公室大厅、办公室话题或工作流运行时，“新会话”会创建独立对话。复用检查每次读取现有 SQLite 绑定，也覆盖旧版本保存的记录。打开已有办公室或工作流历史继续使用原来的 Session。

办公室卡片打开长期保留的大厅对话。项目和话题从各自明确命名的入口创建，打开办公室、话题或工作流历史不会新建项目或重新执行已完成工作。大厅通过 `@` 选择收件人，普通提交保留草稿并提示先选择成员。大厅对话保留用户问题和成员回复，隐藏主助手回执及重复总结。需要处理的错误和审批卡仍然可见，原生轨迹保留完整日志。

对话标题栏右侧使用统一的按钮，在原生右侧栏打开专家团、办公室或工作流详情。专家团侧栏展示团队名称、成员状态和任务进度。办公室详情展示当前项目话题、组长路由和成员实时状态，展开成员可查看职责和最近任务。工作流详情展示本次运行记录的节点进度、前置步骤和结果。办公室和工作流设置统一使用齿轮入口，在当前对话弹窗中复用已有表单，保存仅作用于选中定义，取消、保存失败和成功关闭均保留原对话及侧栏位置。工作流编辑用于后续运行，已有运行记录继续保留。项目入口打开当前办公室的项目页。运行历史通过只读浮层分页展示，展开可查看输入和输出。历史按工作流身份独立查询。定义缺失时不会跳到其他对象。模型和工具日志继续由原生轨迹视图承载。

话题投递保存准确的来源消息与输入水位。原生执行接收成功后才确认成员 Inbox，确认范围限于本次输入快照。执行期间话题发生变化时，上游版本校验可以拒绝回填；办公室保留已完成的输出并单独显示话题投递失败。缺少来源引用的旧消息继续使用话题开场消息。

SQLite schema version 2 保存话题对话绑定与各话题成员 Session ID，迁移保留既有大厅 ID 和消息 JSON，并将旧投递关联到原大厅。话题通过一次零模型初始化轮次成为可保留的普通对话。重复打开使用同一对话，统一时间线仅展示一次。

办公室可指定已有成员为组长，也可在打开后修改。未指定成员的问题进入组长的原生执行链路，定向点名继续交给指定成员。新话题默认通知组长，也可选择仅发布消息。清除组长后恢复显式选择成员的输入方式。旧记录可缺省组长，配置保留成员与对话身份。

组长通过 `office_delegate` 将具体任务交给办公室已有成员，等待落盘的真实结果后汇总。工具校验当前组长、对话和目标成员，复用办公室派发记录。成员回复沿用气泡和原生轨迹。同一工具调用重试时沿用同一投递身份。

<a id="model-experience"></a>
## 模型体验

### 专家团编写与协作

#### 模型看到的内容

bundle 提供 `expert_team_list`、`expert_team_save` 和 `create-expert-team` 技能。提案暂存为审阅卡片；用户确认后保存团队，不启动代理。[上游协作插件](https://github.com/NanmiCoder/dsh-agent-teams) 负责运行时协作工具、指令与结果。

#### Token 影响

已准入工具定义、技能指令和请求的专家目录结果进入模型请求。设置页面本身不调用模型。

#### KV Cache 影响

启用 bundle 会改变 profile 级工具定义和系统指令。成员路由默认跟随团长，除非显式配置。修改已保存配置会改变后续模型请求中的目录。

<a id="known-limitations-and-deferred-work"></a>
## 已知限制与后续工作

- 工作空间状态在单个 Host 进程内串行修改。并发 Host 需要使用不同状态目录。专家团由团长动态规划任务，固定工作流图和长期办公室分别由独立适配器提供。运行兼容检查使用确定性模型适配器，模型质量取决于配置的 provider。
